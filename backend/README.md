# Hustivoo backend

Java 25, Spring Boot, PostgreSQL and Flyway.

## Account and business foundation

- `user.User`: UUID identity, canonical lowercase email, encoded password hash,
  creation/update timestamps. The internal hash getter is excluded from JSON serialization.
- `business.Business`: UUID identity, required name, ISO currency (CHF by default),
  creation/update timestamps.
- `membership.Membership`: UUID identity, lazy required User/Business relationships,
  OWNER or MEMBER role, creation timestamp. There are no cascading parent deletes.

Repositories live beside their entities. Membership lookup methods support queries
by user or business. These repositories are persistence building blocks, not tenant
access controls: future services must authorize each business-scoped operation.
Session authentication endpoints are documented below.
RegistrationService passes BCrypt-encoded hashes to User; never pass plaintext to the entity. Never expose
entities directly through REST; use explicit response DTOs.

## Schema

`V1__create_users_businesses_memberships.sql` creates the tables. Flyway owns schema
changes; `spring.jpa.hibernate.ddl-auto=validate` remains unchanged. Application
UUIDs are generated by JPA. Timestamps use Instant / PostgreSQL TIMESTAMPTZ, with
Hibernate lifecycle timestamps and SQL insertion defaults. Direct SQL updates
must set `updated_at` explicitly.

Constraints enforce unique canonical emails, required nonblank names/hashes,
three uppercase currency letters, valid roles and unique user/business pairs.
Java business construction additionally checks recognized ISO currency codes.
Foreign keys prohibit deleting referenced parents. The membership pair's unique
index covers user lookups; a separate business index covers business lookups.
No single-owner restriction is imposed: more than one owner is permitted.

## Session authentication

Spring Boot 4.1.2 manages Spring Security 7.1.2. Only the security starter is added;
no JWT, OAuth, custom hashing or frontend token storage is used.

| Endpoint | Result |
| --- | --- |
| GET `/api/v1/auth/csrf` | Public, 200 `{headerName, token}`; establishes an anonymous session |
| POST `/api/v1/auth/register` | Public with CSRF, 201 `{id,email}`; does not log in |
| POST `/api/v1/auth/login` | Public with CSRF, 200 `{id,email}` and authenticated session |
| GET `/api/v1/auth/me` | 200 `{id,email}` or 401 |
| POST `/api/v1/auth/logout` | With CSRF, 204; invalidates session and expires cookie |
| GET `/api/v1/health` | Public, unchanged |

Registration/login accept JSON `{email,password}`. Emails are stripped and
lowercased. Registration requires a valid email (at most 320 characters) and a
nonblank password of at least 12 characters, at most 72 characters **and 72 UTF-8
bytes**, reflecting BCrypt's input limit. Passwords are never trimmed. BCrypt
uses cost 12 with library-generated salts. No password composition rules are
imposed. Invalid input is 400, duplicate registration 409, invalid credentials
401 with an identical generic message for unknown email or wrong password.
The database unique constraint arbitrates concurrent registrations.

A successful login explicitly invokes Spring's session-fixation strategy,
rotates the existing session ID, clears the old CSRF token, and saves the security
context in the HTTP session. Credential material is erased by ProviderManager.
Sessions expire after 30 minutes of inactivity and use cookie-only tracking.
JSESSIONID is HttpOnly and SameSite=Lax. Activate `prod` for HTTPS deployments:
`SPRING_PROFILES_ACTIVE=prod` sets Secure=true. Alternatively set
`SESSION_COOKIE_SECURE=true` outside that profile. Local HTTP development defaults
to Secure=false. Do not override production cookie security; terminate TLS and
route frontend/API through the same origin. No cross-origin CORS access is enabled.

All other paths require authentication, with JSON 401/403 rather than login-page
redirects. Unsafe requests without valid CSRF return 403 (including anonymous
requests). There are no CSRF exclusions. The framework's session CSRF repository
and default XOR request handler retain BREACH protection. Security headers prevent
caching authentication and CSRF responses. Do not enable request body, validation
exception, or SQL bind trace logging in production.

### React / Vite integration

Use relative `/api` paths through the existing Vite proxy. The browser manages the
HttpOnly cookie. Do not read the cookie or store authentication tokens in browser
storage. Fetch defaults to same-origin credentials; explicit use is shown here:

```typescript
async function csrfToken() {
  const response = await fetch('/api/v1/auth/csrf', { credentials: 'same-origin' })
  if (!response.ok) throw new Error('Unable to initialize session')
  return response.json() as Promise<{ headerName: string; token: string }>
}

const csrf = await csrfToken()
const response = await fetch('/api/v1/auth/login', {
  method: 'POST',
  credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json', [csrf.headerName]: csrf.token },
  body: JSON.stringify({ email, password }),
})
// Handle 400/401; on success refresh CSRF before the next unsafe request.
if (response.ok) await csrfToken()
```

Keep the returned CSRF token in memory and send its exact header/token pair on
registration, login, logout and future state changes. Refresh it after successful
login and logout. After session expiry, fetch a new token and prompt for login;
do not blindly retry mutations. A CSRF token is not an authentication credential.
Logout clears authentication; a new CSRF bootstrap creates a fresh anonymous
session. The frontend is not modified by this backend implementation.

### Scope and deployment limits

Sessions are currently in the servlet container's memory: restarts log users out,
and multiple instances need sticky routing or a shared session solution. Business
membership authorization is still required in future tenant services. This scope
does not include rate limiting, email verification, password recovery or MFA;
add abuse controls before exposing registration/login broadly.

Authentication tests use actual HTTP requests and cookies against a random-port
server with isolated PostgreSQL. They verify CSRF bootstrap/enforcement, safe
registration responses, normalization, hashing, duplicate and concurrent signup,
validation, generic credential failures, session persistence/rotation, old cookie
rejection, logout, protected API paths and public health access. The original
health slice test isolates the controller; integration tests exercise real filters.

## Business-Onboarding und Mandantentrennung

Die neuen Endpunkte verwenden bewusst den angeforderten Pfad `/api/businesses`.
Die bestehenden Auth-Endpunkte bleiben unter `/api/v1/auth`.

| Methode / Pfad | Verhalten |
| --- | --- |
| POST `/api/businesses` | 201 mit Business-DTO und `Location`; legt automatisch OWNER-Membership an |
| GET `/api/businesses` | 200 mit Array ausschliesslich eigener Membership-Unternehmen; sonst `[]` |
| GET `/api/businesses/{id}` | 200 bei Membership, sonst 404 |

Beispiel für POST (Session-Cookie und gültigen `X-CSRF-TOKEN` mitsenden):

```json
{
  "name": "Studio Beispiel",
  "industry": "Design",
  "legalForm": "Einzelfirma",
  "country": "CH",
  "currency": "CHF"
}
```

`name` ist erforderlich und auf 255 Zeichen begrenzt. `industry` und `legalForm`
sind optionale Freitexte mit maximal 120 Zeichen; leere Werte werden zu null.
Land und Währung sind ISO-Codes, werden getrimmt und grossgeschrieben. Fehlende
oder null-Werte erhalten CH beziehungsweise CHF; explizit leere oder ungültige
Codes werden abgelehnt. Die Länder-/Währungskombination wird nicht eingeschränkt.
Das Response-DTO enthält ausschliesslich id, name, industry, legalForm, country,
currency, createdAt und updatedAt, keine Benutzer oder Membership-Entities.

`BusinessService` ermittelt die Identität bei jedem Aufruf aus dem Security
Context und prüft, dass der Benutzer noch existiert. Weder Request-Body noch
Query-Parameter oder Header liefern die autorisierende User-ID. Business und
OWNER-Membership werden in derselben Transaktion gespeichert; schlägt eine
Operation fehl, wird beides zurückgerollt. Auch direkte Service-Aufrufe prüfen
die Identität; Leseabfragen filtern bereits in der Datenbank nach Membership.
OWNER und MEMBER dürfen lesen. Es gibt keine administrativen Ausnahmen.

Fremde und unbekannte IDs liefern identisch 404 `{"error":"Business not found"}`.
Ungültige Eingaben/UUIDs liefern 400 `{"error":"Invalid request"}`. Anonyme Zugriffe
liefern 401; unsichere Requests ohne gültigen CSRF-Token können bereits zuvor mit
403 abgewiesen werden. Persistenzfehler liefern eine generische 500-Antwort ohne
interne Details. Vorhandene Session- und CSRF-Konfigurationen bleiben unverändert.

`V2__add_business_onboarding_fields.sql` ergänzt industry, legal_form und country
mit Constraints. Bestehende Unternehmen erhalten CH; ihre Währung bleibt erhalten.
V1 bleibt unverändert. Hibernate verwendet weiterhin `validate`.

Die PostgreSQL-Integrationstests decken Erstellung/Defaults/OWNER-Zuordnung,
Eingabevalidierung, anonyme Zugriffe, CSRF, mehrere Unternehmen pro Benutzer,
MEMBER-Lesezugriff, IDOR und gefälschte Client-Identitäten ab. Ein temporärer
Datenbank-Trigger im isolierten Testcontainer erzwingt einen Membership-Fehler,
um den vollständigen Rollback nachzuweisen. Ein separates Testschema prüft den
V1-zu-V2-Upgrade mit vorhandenen Daten.

Keine neuen Abhängigkeiten, Frontend-Änderungen oder automatisch angelegten
Unternehmen bei Registrierung. Die neuen Endpunkte bearbeiten oder löschen
keine Unternehmen/Memberships. Künftige tenantbezogene Services müssen denselben
Membership-Filter anwenden; allgemeine Repository-Methoden sind kein Ersatz für
Autorisierung.

## Kundenverwaltung

V3 (`V3__create_customers.sql`) ergänzt `customers`; V1 und V2 bleiben unverändert.
Jeder Kunde hat eine UUID und eine unveränderliche, verpflichtende Business-ID
mit Foreign Key (kein Cascade-Delete). Ein zusammengesetzter Unique-Key
`(business_id, id)` ermöglicht später mandantensichere zusammengesetzte Referenzen
von Rechnungen/Projekten. Der Index `(business_id, archived, display_name)` unterstützt
Business-Listen. Kein Hard-Delete-Endpunkt: Archivierung erhält Referenzierbarkeit.

Felder: type (PRIVATE/COMPANY), displayName (Pflicht, 255), companyName (255),
firstName/lastName (120), email (320), phone (50), street (255), postalCode (20),
city (120), country (2, Default CH), notes (4000), archived (Default false),
createdAt/updatedAt (Instant/TIMESTAMPTZ). Alle Kontaktfelder ausser displayName
sind optional. Leere optionale Strings werden null, Länder grossgeschrieben.
ISO-Land, E-Mail und Längen werden validiert; der Anzeigename bleibt unabhängig
von Firmen-/Personennamen. Doppelte Namen oder E-Mails sind erlaubt.

Basis: `/api/businesses/{businessId}/customers`

| Methode | Pfad | Antwort |
| --- | --- | --- |
| GET | Basis | 200 Array, standardmässig nur aktive Kunden |
| POST | Basis | 201 Customer-DTO mit Location |
| GET | `/{customerId}` | 200 Customer-DTO |
| PUT | `/{customerId}` | 200, vollständiger Ersatz der editierbaren Kontaktfelder |
| PATCH | `/{customerId}/archive` | 200, archived=true |
| PATCH | `/{customerId}/restore` | 200, archived=false |

GET unterstützt `search` (maximal 320 Zeichen; case-insensitive Teilzeichenfolge
in Anzeigename, Firma oder E-Mail) und `includeArchived=true` (aktive **und**
archivierte). Prozent/Unterstrich werden als normale Suchzeichen behandelt.
Ergebnisse sortieren nach Anzeigename und UUID. POST/PUT nehmen Kontaktfelder
entgegen, keine autorisierende User-ID, Business-ID oder archived-Eigenschaft.
PATCH benötigt keinen Body. Alle Schreiboperationen benötigen Session und CSRF.

`CustomerService` verwendet die vorhandene BusinessService-Membership-Prüfung aus
dem Security Context. Jedes Detail/Update/Archivieren sucht zusätzlich mit
Customer-ID **und** Business-ID. OWNER und MEMBER erhalten identische Lese- und
Schreibrechte für operative Kundendaten; weitergehende Rollenregeln waren bisher
nicht definiert. Diese Entscheidung ist durch einen MEMBER-Schreibtest abgesichert.
Fremde Businesses, fremde Kunden und unbekannte UUIDs liefern gleichermassen
404 `{"error":"Customer not found","fields":{}}`. Validierungsfehler liefern
400 mit `error` und gegebenenfalls feldbezogenem `fields`-Objekt, ohne beanstandete
Werte oder interne Exception-Details.

Verifikation: `./mvnw verify` mit Java 25 erfolgreich, 42 Tests bestanden.
PostgreSQL/Testcontainers prüfen CRUD ohne Hard-Delete, Suche, Archivierung,
Wiederherstellung, Validierung, Membership, MEMBER-Schreiben, manipulierte
Business-/Customer-IDs, 401, CSRF und Flyway/Hibernate mit V3. Bestehende Auth- und
Onboarding-Tests bleiben erfolgreich.

Grenzen: Listen sind derzeit nicht paginiert; für grosse Datenbestände folgen
Pagination und ggf. Suchindizes. Gleichzeitige Änderungen nutzen aktuell
Last-Write-Wins; kein Audit-Log oder optimistischer Versionskonflikt. Die
Kontaktverwaltung erstellt noch keine Rechnungen, Angebote oder Projekte.

### Datenmodell und Migration

`V5__create_services.sql` ist die nächste Migration nach V4; V1–V4 bleiben unverändert.
Die Tabelle `services` hat UUID-IDs, `business_id` als Foreign Key, Name (255,
Pflicht), Beschreibung (4000, optional), Kategorie (120, optional), Einheit,
`unit_price NUMERIC(19,2)`, Währung (3 Zeichen, Default CHF),
`tax_rate NUMERIC(5,2)` (optional), Aktivstatus (Default true) und Zeitstempel.
Preise sind nicht negativ; Steuersätze liegen zwischen 0 und 100. Einheiten sind
HOUR, DAY, FIXED, PIECE, MONTH. Indizes unterstützen Business-/Status-/Name-,
Preis- und Kategorieabfragen. `(business_id, id)` ist zusätzlich eindeutig für
spätere mandantengebundene Dokumentreferenzen. Hibernate bleibt auf `validate`.

Alle Beträge sind in Java `BigDecimal`. Mehr als zwei Dezimalstellen werden per
Bean Validation abgelehnt, nicht still gerundet. API-Antworten verwenden für
Preis und Steuersatz **Dezimalstrings mit zwei Nachkommastellen**, damit JavaScript
auch grosse Beträge exakt erhält. Die Eingabe erfolgt ebenfalls als Dezimalstring.
Maximaler Preis: `99999999999999999.99`. Währungen werden normalisiert und mit
`java.util.Currency` validiert. Leere optionale Texte werden null.

| GET | `/{serviceId}` | 200, auch für archivierte Leistungen |

```json
{

  "category": "Beratung",
  "unit": "HOUR",
  "unitPrice": "95.00",
  "currency": "CHF",
  "taxRate": "8.10"

```

`updatedAt`. Optionaler Steuersatz bleibt null, wenn nicht gesetzt. `active` wird
nur über Archivieren/Wiederherstellen geändert. Kein DELETE-Endpunkt.

### Sicherheit und spätere Dokumente

Jeder Service-Aufruf prüft zuerst die Membership über `BusinessService` und die
Identität aus dem Security Context. OWNER und MEMBER dürfen lesen und schreiben.
Alle Ressourcenzugriffe sind zusätzlich durch `businessId` eingeschränkt. Fremde
und unbekannte Businesses/Leistungen erhalten dieselbe JSON-404-Antwort
`{"error":"Service not found","fields":{}}`. Schreibzugriffe verwenden die
bestehende Session-/CSRF-Konfiguration. Updates und Archivierung laufen in
Transaktionen mit gesperrter Leistungszeile. DTOs enthalten keine User-ID zur
Autorisierung. Validierungsfehler liefern 400 mit sicheren Feldmeldungen;
Datenbankfehler werden ohne interne Details als 500 ausgegeben.

Leistungs-IDs bleiben bei Preisänderung und Archivierung stabil. Künftige
Angebots-/Rechnungspositionen müssen Beschreibung, Einheit, Preis, Währung und
Steuersatz beim Erstellen als eigene Snapshots speichern und die Referenz über
Business und Leistungs-ID absichern. Historische Dokumente dürfen nicht aus dem
aktuellen Katalogpreis neu berechnet werden. Diese Dokumentmodule werden noch
nicht implementiert.

### API

Basis `/api/businesses/{businessId}/quotes`. Schreibende Aufrufe benötigen Session und CSRF.

| Methode | Pfad | Ergebnis |
| --- | --- | --- |
| GET | Basis | 200, Liste (ohne Positionen/Notizen); `search` (≤320, Nummer/Kunde), `status` |
| POST | Basis | 201 + Location, neuer Entwurf mit Nummer |
| GET | `/{id}` | 200, vollständiges Angebot |
| PUT | `/{id}` | 200, nur DRAFT (sonst 409); ersetzt Kopf und alle Positionen |
| DELETE | `/{id}` | 204, nur DRAFT (sonst 409) |
| PATCH | `/{id}/send` | DRAFT → SENT; 409 ohne Positionen |
| PATCH | `/{id}/accept` | SENT → ACCEPTED |
| PATCH | `/{id}/reject` | SENT → REJECTED |
| GET | `/{id}/pdf` | 200 `application/pdf`, `attachment; filename="Angebot-ANG-0001.pdf"`, `no-store` |

Request (POST/PUT):

```json
{
  "customerId": "…", "issueDate": "2026-11-18", "validUntil": "2026-12-18", "currency": "CHF",
  "introductionText": "…", "closingText": "…", "notes": "nur intern",
  "items": [
    { "serviceId": "…", "quantity": "1.5" },
    { "description": "Hosting", "quantity": "12", "unit": "MONTH", "unitPrice": "29.00", "taxRate": "8.10" }
  ]
}
```

Mit `serviceId` übernimmt der Server fehlende Beschreibung, Einheit, Preis und
Steuersatz aus dem Katalog (Steuersatz null → 0); mitgesendete Werte überschreiben
sie (z. B. angepasster Preis). Freie Positionen brauchen alle Werte. `currency`
fehlt → bisherige bzw. Business-Währung. Summen, Nummer, Status, Snapshots,
Business- und User-IDs werden **nie** vom Client übernommen; unbekannte Felder wie
`grandTotal` werden ignoriert und neu berechnet. Grenzen: 200 Positionen, Texte
4000 Zeichen, Menge > 0 mit ≤ 3 Dezimalen (≤ 999'999'999.999), Preis ≥ 0 mit ≤ 2
Dezimalen, Steuersatz 0–100, jeder Betrag ≤ 99'999'999'999'999'999.99.
Beträge in Antworten sind Dezimalstrings; zusätzlich `taxGroups` (Basis und Steuer pro Satz).

Fehler: 400 `{"error":"Invalid request","fields":{…}}` mit Feldschlüsseln wie
`items[0].unitPrice`; 404 `{"error":"Quote not found","fields":{}}`; 409 mit
`Quote is not editable`, `Invalid status transition`, `Quote has no items`.

### Statusregeln

```
DRAFT ──send──▶ SENT ──accept──▶ ACCEPTED (final)
  │                └──reject──▶ REJECTED (final)
  └─ bearbeiten / löschen nur hier
```

Nur Entwürfe sind bearbeit- und löschbar (gelöschte Nummern werden nicht neu vergeben).
Versendete Angebote werden nicht gelöscht, sondern angenommen oder abgelehnt.
Angenommene/abgelehnte Angebote sind unveränderlich – geprüft im Service (409) und
zusätzlich per Datenbanktrigger. Ein abgelaufenes SENT-Angebot kann bewusst noch
angenommen werden (späte Zusage); die Oberfläche kennzeichnet es als „Abgelaufen“.
Gleichzeitige Änderungen sind über eine Zeilensperre serialisiert.

### Nummernvergabe

`ANG-0001`, `ANG-0002`, … pro Business über
`INSERT … ON CONFLICT DO UPDATE … RETURNING` auf `quote_number_counters` in derselben
Transaktion wie das Angebot. Die Zeilensperre serialisiert parallele Anfragen; bei
Rollback wird der Zähler mit zurückgerollt. Validierung erfolgt vor der Vergabe, ungültige
Anfragen verbrauchen keine Nummer. Ab 10'000 wird die Nummer länger (`ANG-10000`).

### Snapshots und Mandantentrennung

Jede Position speichert Beschreibung, Einheit, Preis, Steuersatz und Zeilenbeträge;
spätere Katalogänderungen oder Archivierungen wirken sich nicht aus. Kunden-Snapshot
(Nummer, Name, Firma, Kontakt, Adresse, Land, E-Mail) und Absendername werden bei jedem
Speichern eines Entwurfs und ein letztes Mal beim Versand aktualisiert, danach eingefroren.
Archivierte Kunden/Leistungen bleiben in Entwürfen, die sie bereits verwenden, erlaubt,
können aber nicht neu gewählt werden. Leistungen in fremder Währung sind nur mit
explizitem Preis erlaubt.

Jeder Aufruf prüft zuerst die Membership aus dem Security Context (`BusinessService`);
OWNER und MEMBER haben gleiche Rechte. Angebote, Kunden und Leistungen werden nur über
ID **und** Business-ID geladen. Fremde und unbekannte Angebote/Businesses liefern
byte-identische 404-Antworten (auch für den PDF-Download); fremde und unbekannte
Kunden-/Leistungs-IDs im Body identische 400-Antworten.

### Berechnung und Rundung

`QuoteCalculator`, ausschliesslich `BigDecimal`:

1. `lineSubtotal = quantity × unitPrice`, kaufmännisch (HALF_UP) auf die kleinste Einheit der Währung
2. `lineTax = lineSubtotal × taxRate / 100`, ebenso gerundet
3. `lineTotal = lineSubtotal + lineTax`
4. `subtotal`/`taxTotal` = exakte Summe der gerundeten Zeilen; `grandTotal = subtotal + taxTotal`

Rundung pro Zeile, damit gedruckte Zeilen und Summen immer übereinstimmen. Kleinste
Einheit nach ISO 4217: CHF/EUR/USD/GBP 0.01, JPY 1 (gespeichert als `.00`). Währungen mit
drei Nachkommastellen (z. B. KWD) werden abgelehnt. **Keine 5-Rappen-Rundung** für CHF:
Angebote und spätere Überweisungen/QR-Rechnungen sind rappengenau; eine
Bargeldrundung wäre eine separate Rechnungsfunktion. Hinweis: Die MWST pro Zeile kann
um wenige Rappen von einer Berechnung auf der Satzsumme abweichen.

### PDF

Apache PDFBox 3.0.8 (Apache-2.0) ist die einzige PDF-Abhängigkeit. Der Renderer verwendet
ausschliesslich Snapshot-Daten des Angebots und die gespeicherten Serverbeträge; er
formatiert, rechnet aber nie neu. Versendete Angebote behalten dadurch exakt ihren Inhalt.

**Aufbau** (`digital.margraf.hustivoo_backend.document`, wiederverwendbar für Rechnungen):

| Klasse | Aufgabe |
| --- | --- |
| `DocumentTheme` | Primär-/Sekundärfarbe, Text-, Linien- und Warnfarben, optionale Fusszeilennotiz; `hustivoo()` als Standard |
| `DocumentSender` | Absendername, Adress- und Kontaktzeilen, Logo (PNG/JPEG); leere Angaben entfallen |
| `DocumentFonts` | Eingebettete Inter-Fonts, Zeichenprüfung, Fallback |
| `PdfCanvas` | Seiten, Text, Umbruch ohne Abschneiden, Linien, Bilder |

`QuotePdfRenderer.render(quote, sender, theme, homeCountry)` ist der Einstiegspunkt für
späteres Branding (Logo, Farben, Fusszeile). Heute liefert `render(quote, business)` den
Snapshot-Absendernamen mit dem Hustivoo-Theme; eine Einstellungsseite gibt es bewusst nicht.

**Layout (A4):** Ränder 22 mm. Briefkopf mit Unternehmensname (bei Bedarf Logo,
Adresse, Kontakt) links und gesperrtem „ANGEBOT“, Nummer und dezentem „ENTWURF“-Label
rechts. Darunter zwei ausbalancierte Spalten „Empfänger“ (Name, Firma, Kontakt, Adresse,
Land bei Auslandskunden, Kundennummer) und „Angebotsdetails“ (Nummer, Datum, Gültigkeit,
Währung). Betreffzeile „Angebot für …“, Einleitung mit lesefreundlicher Zeilenlänge.
Die Tabelle hat dezente Versalien-Spaltenköpfe, eine dunkle Haarlinie, hellgraue
Zeilentrenner, keine Zellrahmen, rechtsbündige Beträge und zweistufige Beschreibungen
(erste Zeile fett, Details grau). Die Zahlenspalten werden pro Dokument an den längsten
Wert angepasst, Beträge werden nie abgeschnitten. Summenblock: Zwischensumme, MWST je
Satz („MWST 8.1 % auf 951.00“, bei steuerfreien Angeboten „MWST CHF 0.00“), dunkelgrüne
Linie, „Total“ gross und fett, Hinweis „Gültig bis … · Beträge in CHF“. Danach folgt der
Abschlusstext, nur wenn gespeichert. Interne Notizen erscheinen nie. Die Fusszeile
enthält Unternehmensname, optionale Kontakt-/Zahlungsangaben (bis zwei Zeilen, Einträge
werden nie getrennt), „Angebot ANG-…“ und „Seite X von Y“. Metadaten: Titel, Betreff,
Autor, Sprache de-CH.

**Seitenfluss:** Seiten entstehen erst, wenn Inhalt gezeichnet wird, daher gibt es keine
leeren Seiten.
- Der Tabellenkopf steht nie allein, sondern immer mit dem Beginn einer Position.
- Positionen bleiben zusammen. Nur eine Position, die höher als eine Seite ist, wird
  zeilenweise umbrochen; Wörter werden dabei nie getrennt.
- Folgeseiten haben einen schlanken Laufkopf, den wiederholten Tabellenkopf und
  „Übertrag von Seite N“. Das Seitenende zeigt „Übertrag“ als exakte Summe der bis dahin
  gedruckten Positionsbeträge.
- Summenblock und ein kurzer Abschlusstext (bis 6 Zeilen) werden zusammengehalten.
- Inhalt endet mindestens 28 pt über der Fusslinie.

**Typografie:** Inter 4.1 (Regular, SemiBold, Bold) unter der SIL Open Font License 1.1,
mitgeliefert unter `src/main/resources/fonts/inter/` inklusive `OFL.txt`. Die Fonts
werden als Subset eingebettet; zur Laufzeit wird nichts nachgeladen und kein
System-Font verwendet. Abgedeckt sind alle europäischen Lateinschriften (Umlaute,
französische Akzente, Ł, Ș/Ț, Ő/Ű, Æ/Ø …), Griechisch, Kyrillisch, €, typografische
Anführungszeichen und Striche. Fallback: zuerst NFC-Normalisierung, dann Zerlegung in
Grundbuchstabe plus Akzent. Nicht darstellbare Zeichen werden sichtbar als „?“ gedruckt
und mit Code-Point (ohne Text) als WARN geloggt, also nicht stillschweigend ersetzt.

### Bekannte Einschränkungen

- Businesses speichern weder Adresse noch Logo, Kontaktangaben, UID oder
  Bankverbindung. Das PDF zeigt deshalb nur den Unternehmensnamen; nichts wird erfunden.
  Renderer und `DocumentSender` unterstützen diese Angaben bereits, sobald das
  Business-Modell sie liefert.
- CJK, Emoji und rechts-nach-links-Schriften (Hebräisch, Arabisch) deckt Inter nicht ab.
  Sie erscheinen als „?“ mit Log-Warnung. PDFBox setzt kein RTL und keine Ligaturen,
  deshalb wurde bewusst kein unvollständiger Zweitfont ergänzt. Echte Unterstützung
  bräuchte einen Noto-CJK/RTL-Font und Text-Shaping.
- Ohne OpenType-Features: Inter-Ziffern sind proportional, nicht tabellarisch. Die
  Beträge sind rechtsbündig, Dezimalpunkte können minimal versetzt stehen. Kerning
  wird nicht angewendet.
- Die Empfängeradresse steht links, ohne Fensterkuvert-Raster nach SN 010130. Das
  Layout ist auf den digitalen Versand ausgelegt.
- Bei extrem grossen Mengen oder Beträgen wird die Beschreibungsspalte schmaler,
  weil Beträge Vorrang haben.
- Keine Paginierung der Liste, keine Rabatte, keine Duplizier-/Rechnungsumwandlung,
  kein E-Mail-Versand („gesendet“ ist eine manuelle Markierung).
- Angebotssprache und Formate sind Deutsch/Schweiz.
